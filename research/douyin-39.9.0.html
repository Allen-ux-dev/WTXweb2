抖音 iOS 39.9.0
静态分析报告

一个 975 MB 的二进制里，藏着一本采集账本、八条上报链路，和一只过于灵敏的摇一摇。

样本抖音(39.9.0)_静态脱壳.ipa（727 MB，解密版）
方法Mach-O 静态分析 · 字符串提取 · 资源解包
是否抓包否（结论均为静态证据）
日期 / 版本2026-11-20 · v1.1
结论边界只能证明「有这个能力 / 有这个配置项」，不能证明「此刻正在执行」

摘要

抖音不是「偷偷采集」，而是采集到极致，并且自己登记了一本账。

二进制里有一张把「系统 API」直接映射到「数据类型」的规则表，共 34 个采集标签； 配套 1538 个隐私检查点、23 类 Apple 数据申报、一套 C2PA + TC260 的 AI 内容水印。 这部分做得比大多数同类 App 完整，是可验证的，不是公关话术。

但把账本摊开数一遍，会看到另一个结构：

  • 33 类数据里，用户自己能决定的只有 3 类（通讯录、经纬度、剪贴板读取）； 12 类只能去系统设置关权限；剩下 18 类没有任何开关——包括全部 8 类传感器， 因为 iOS 对加速度计、陀螺仪本身就不弹授权框。
  • 三条关不掉的链路：设备指纹 dtrait（重置 IDFA、卸载重装也能绑回同一设备）、 相册 EXIF 位置（连「已经上传的」历史图片都算）、以及一条发往阿里 wgo.mmstat.com 的第三方统计链路（读 IDFA）。
  • 摇一摇的「灵」是产品设计：6 处独立实现，阈值 shake_effect.ios_threshold 由服务端下发， 连麦场景默认 0.1 秒采一次样。改松紧不需要发版。

所以准确的描述不是「暗中收集」，而是：默认全开 + 开关隐藏 + 参数不可观测。

一句话：它把「告知」做到了极致，于是「克制」就成了可选项。

只想看结论：直接跳 0. 一句话结论 / 9.6 判断。
想看怎么证明的：从 2. 采集清单 开始。

0. 一句话结论

抖音不是「偷偷采集」，而是「采集到极致并且自己登记了清单」。 真正的信息不对称不在「有没有告诉你」，而在三处「你关不掉、也看不见」： 设备指纹（dtrait）、相册 EXIF 位置、第三方统计链路（阿里 mmstat）。

2.4 唯一被我判定为「有独立弹窗开关」的隐藏项：相册 EXIF 位置

  • 文案：「是否允许使用相册内容的位置信息？」
  • 关闭后：「将不使用本地相册和已经上传的相册内容中的位置信息」
  • 配置键：asset_location、uploaded_assets_location、studio_publish_fetch_asset_location、aigc_album_disable_access_exif_location

注意「已经上传的」这句：即使你之后关了，服务器侧历史图片的位置信息仍在被使用。

3. 三条「你关不掉」的链路

3.1 dtrait：一次授权，终身可认

TTInstallIDManager+Dtrait 是设备特征的绑定机制：

请求：https://log.snssdk.com/service/2/dtrait/
请求头：x-tt-device-dtrait / x-tt-device-signal / x-tt-device-dtrait-token
字段：encrypted_dtrait、dtrait_token、bind_dtrait、dtrait_pre、dtrait_stage

配套还能看到 kTTResetedIDFA、kTTResetedVendorID、kTTResetedDeviceID、kTTResetedInstallID —— 说明「重置追踪标识」是被单独处理的一种状态。

实际意义：你把 IDFA 重置、甚至卸载重装，dtrait 仍可以把新的 install_id / did 绑回同一台设备。 这是「它好像一直认得我」的技术来源，也是隐私政策里最难说清的一层。

3.2 广告侧的传感器与电池采集

AWEAdPitayaHARServiceDataCollectionManager
feed_ad_har_service_sensor_data_enable
feed_ad_har_service_battery_enable
search_ad_har_service_sensor_data_enable

广告 SDK 内部有个 HAR 数据采集服务，读传感器 + 电池状态，供端侧模型（Pitaya）判断场景。 这个开关是配置项，用户在设置里看不到。

3.3 阿里的第三方统计链路

UTAnalytics / UTOirginalCustomHitBuilder
https://wgo.mmstat.com/cf.linkpartner.1.1 / 1.3 / 1.4 / 1.5 / 2.4
读取 ASIdentifierManager.advertisingIdentifier

抖音内置了阿里巴巴的 UT 统计 SDK，用于电商/淘宝联盟归因，读 IDFA 后上报 wgo.mmstat.com。 这是一条离开字节域名体系的数据链路，多数人没注意到。

「灵」的三个技术原因：

1. 阈值在服务端（shake_effect.ios_threshold），改配置即可调松紧，用户无法观测。 2. 采样密：默认 0.1 秒一次，走路/抬腕都可能触发。 3. 不止摇：BDASplashTwistView、BDASplashCommonTwistModel、BDASplashClickSlideViewModel —— 摇一摇、扭一扭、滑一滑三种「非点击交互」并存，本质是把误触转化为点击率。

8. 结论（事实层）

「暗中收集」这个说法需要修正为「默认全开 + 开关隐藏 + 参数不可观测」。

  • 它其实登记得比大多数 App 都清楚：34 项自报清单、1538 个检查点、AI 内容还按国标打标。
  • 真正的不对称是：33 项里你只能自己决定 3 项，其余要么去系统设置翻三层菜单，要么根本没有开关（传感器就是这样，iOS 本身不给授权框）。
  • 最值得注意的是 dtrait：它让「重置 IDFA / 卸载重装」这类常规反抗手段部分失效。
  • 摇一摇的灵敏度不是 bug，是产品设计——而且阈值握在服务端。

待验证：以上全部为静态证据。要确认实际行为，需要抓包对比 （重点看 service/2/dtrait、weasel/v1/info、app_log 三处的请求体）。

事实摆完了。它意味着什么，见下一章。

9. 评价与反思（判断层）

本章是判断，不是事实。前 8 章是「它是什么」，这一章是「这意味着什么」。
每个判断后面标了对应的行为证据编号（见 9.3）。

9.1 先修正一个说法

「抖音在暗中收集用户信息」这句话，只能算对了一半。

准确的说法是：默认全开 + 开关隐藏 + 参数不可观测。

它甚至自己登记了一份比绝大多数 App 都完整的清单（34 个采集标签、1538 个隐私门禁、AI 内容按国标打标）。 所以问题不是「没告诉你」，而是「告诉了，但告诉的方式本身构成了一种新的不透明」。

9.2 「合法到极致」的三层结构

第一层：合规的度量单位是「告知」，不是「克制」

这是最根本的一层。法律要求的是披露充分、授权到位，没有任何一条要求少采。 于是理性的做法必然是：把能采的都采了，然后为每一个动作补一张凭证。

于是出现一个反直觉的现象 —— 检查点的密度和采集量是正相关的。 采集面越大，需要过的隐私门禁越多，合规报告越厚，看上去越规范。

证据链：E1（34 项清单，量在扩）+ E2（1538 个 bpea 检查点，章在盖）
1538 这个数字不是「克制了 1538 次」，是「为 1538 个动作各自盖了章」。

盖满章的东西，反而显得干净。

第二层：审计成本被转嫁给了用户

公司有法务团队去证明「我告知了」。用户只有一双眼睛，去看：

  • 藏在「我 → 设置 → 隐私设置」第三层的开关；
  • 一句「不使用本地相册和已经上传的相册内容中的位置信息」里，「已经上传的」四个字意味着什么。
证据链：E5（开关分层）+ E6（EXIF 文案措辞）

披露做得越完整，越没人读得完 —— 而「读不完」本身就已经完成了合规。 这是一套自我闭合的结构：披露的完备性，恰好构成了免于被追问的理由。

第三层：最有效的那部分，无法被语言化

dtrait 永远进不了隐私政策的人话部分。你没法写：

「我们会用设备特征在您重置 IDFA 后继续识别您。」

太绕，也太长。于是它合法地待在 x-tt-device-dtrait 这个请求头里， 等你某天发现「它怎么还认识我」，再去猜。

证据链：E3（TTInstallIDManager+Dtrait 全套字段）

第三层是最值得警惕的：它不是隐藏，是技术上正确、语言上不可达。

9.3 行为证据汇总（观点 ↔ 代码事实）

编号判断对应的代码层面事实
E1采集面是主动扩张的二进制内有 34 个 XXX_Collection 标签的规则表，逐条映射到系统 API；新增能力即新增标签
E2合规凭证的密度1538 个 bpea- 前缀隐私门禁，覆盖相册、仿板、定位、传感器等每一处访问
E3反抗手段被吸收TTInstallIDManager+Dtrait 把设备特征绑到 install_id；并存 kTTResetedIDFA/VendorID/DeviceID/InstallID 四组重置状态字段
E4默认值是「开」33 项里默认开启；能主动询问的极少，相册 EXIF 位置是其中一项
E5开关的可见性递减A 级（自己能决定）3 项 / B 级（只能去系统设置）12 项 / C 级（无任何开关）18 项

9.4 为什么「比同行好」反而更讽刺

这是个有趣的心理结构。

  • 那些连清单都没有的 App，你根本没期待，也就谈不上失望。
  • 抖音把该做的都做了，还多做了一点（C2PA + TC260 水印，国内真没几家做到）， 结果你一数：33 项里我能决定的只有 3 项。

做得越好，期望越高，落差越明显。 讽刺感来自「它有能力做得更好，但它选择的是做完」。

还有一处很漂亮的对比：

它会给 AI 生成的内容打水印、写 C2PA 元数据、标 TC260 国标 ——
但没有机制告诉你，你看这条视频的行为被同步给了几个下游。
证据链：E8（阿里链路）+ E9（广告 HAR 采集）+ 第八章的 8 个日志域

内容的「来源」被标记得清清楚楚，数据的「流向」却没有任何标注。 这是整个报告里我认为最值得记住的一句话。

9.5 值得肯定的三处（保持平衡）

1. 自查清单本身是真的。34 项标签映射到具体 API，不是公关话术，是可验证的。 2. SKAdNetwork 只声明 5 个。广告 SDK 普遍塞几十个，这是真克制。 3. AI 内容合规走在前面。C2PA + TC260 双标，2026 年还有大量 App 没做。

另外要区分一件事：传感器无需授权是 iOS 的平台约束，不是抖音的选择。 加速度计、陀螺仪、磁力计本来就不弹框，谁都用得上。把它算进「抖音很坏」不公平； 但把它算进「你无法拒绝」是对的。

9.6 判断

这套系统的核心不是「收集」，是「让你无法验证它收集了什么」。

能关的你关了，但不知道关了之后它还在发什么； 能重置的你重置了，但 dtrait 会把线索接回去； 能感觉到的你感觉到了（摇一摇的灵），但改不了（阈值在服务端）。

三个层次对应三种反抗方式的失效：权限、重置、感知。

如果只记一句话，记这个：

它把「告知」做到了极致，于是「克制」就成了可选项。

复现路径

# 1. 解包
unzip -q "抖音(39.9.0)_静态脱壳.ipa" -d ipa

# 2. 定位 ObjC 类名/方法名区段（拿到 addr 与 size）
otool -l ipa/Payload/Aweme.app/Frameworks/AwemeCore.framework/AwemeCore \
  | grep -A3 -E "sectname (__objc_classname|__objc_methname)"

# 3. 按偏移抽出（__TEXT 的 fileoff = 0，所以 addr 就是文件偏移）
CORE=ipa/Payload/Aweme.app/Frameworks/AwemeCore.framework/AwemeCore
dd if="$CORE" of=classnames.raw bs=1M iflag=skip_bytes,count_bytes \
   skip=$((0x2a7e4a10)) count=$((0x4c3950))
strings -a classnames.raw | sort -u > classnames.txt

# 4. 提取完整字符串集
strings -a -n 5 AwemeCore > core.strings

一个关键技巧：二进制的中文不是 UTF-8 存的，而是 UTF-16LE（__ustring）。 只跑 strings 会漏掉所有中文文案。需要按 UTF-16LE 分块解码后再抓 CJK 连续段， 这也是本文能找到「摇一摇」「已上传的相册内容」这类文案的原因。

# 核心逻辑
s = chunk.decode('utf-16-le', 'ignore')
re.finditer(r'[\u4e00-\u9fa5][\u4e00-\u9fa5\w，。、：；！？“”（）%\-—·…《》 ]{1,60}', s)
